# 0023 — The scenario catalog lives in the database and is maintained by admins through one Excel workbook; a default workbook ships with the system

**Status:** Accepted 2026-11-13 (the user chose an admin-maintained workbook as the system's catalog and its default); the import details are **Proposed** in [features/scenario-catalog](../features/scenario-catalog/README.md). Revised 2026-11-13, before anything was built: `species` holds only the codes the scenarios use, not the whole ASFIS list (user). Revised 2026-11-16, before the workbook was built: `species` also keeps ASFIS's family and order or higher taxa, and the shipped species default is a CSV in git (`catalog/data/species.csv`) loaded by `surimi-backend seed-species`, built first (user). Revised again 2026-11-16: `species` holds the **whole** ASFIS list again (13,567 rows plus manual rows), searched through a full-text index (user)
**Date:** 2026-11-13
**Related:** supersedes the storage and upkeep of [0017](0017-scenario-catalog-from-partner-config.md) (its decisions 1, 3 and 5); [features/scenario-catalog](../features/scenario-catalog/README.md), [features/harvest-control-rules](../features/harvest-control-rules/README.md), [0018](0018-harvest-control-rules-per-user-and-scenario.md)

## Context

- Since 2026-11-05 the catalog is one JSON file per scenario, generated by a
  developer from the partner repos and the ASFIS list and committed
  ([0017](0017-scenario-catalog-from-partner-config.md)). Any change, even one
  group name, needs a developer, a commit and a deploy.
- Some data exists in no repo: `aegean_sea` has no published group mapping
  (its MICE model, SURIMI-project issue #154, is unpublished), and `GRM`,
  `OTH`, `YRC` are not in ASFIS. Someone has to type them in.
- The partner inputs the catalog was built from did not change between
  2026-11-05 and 2026-11-13 (**Read from source**: SURIMI-Ecopath
  `156c130...735cc98` touches no `.semantics` or model file;
  SURIMI-fisheries-authority unchanged), so automatic refresh from the
  partners brings little today.
- The controller's contract gives each species only `species_code`,
  `length_class`, `age`, `life_stage` (**Read from source**, SURIMI-protocol
  `be08fd33`). Names, groups and HCR eligibility have no gRPC source.
- A species code means the same species in every scenario (FAO ASFIS
  `Alpha3_Code`): the 49 codes `aegean_sea` and `northwestern_med` share have
  the same names (**Verified** 2026-11-13 on the catalog files). Groups, life
  stages and HCR eligibility differ per scenario: `ANE` is two groups in
  `northwestern_med` (38, 39) and one in `anchovy_bay` (7); group key `4` is
  *Cod* in `anchovy_bay` only.
- 0017 rejected "database tables edited by admins" because there is no admin
  UI before phase 10, hand copies drift from the partner repos, and a database
  is harder to review than git.

## Decision

The catalog moves into PostgreSQL and **admins alone** maintain it, through one
Excel workbook (`.xlsx`) whose sheets are the tables, column for column:
`species` (global: every ASFIS species, 13,567 rows, plus admin rows for
codes ASFIS lacks, with `source` = `asfis` or `manual`), and, per scenario with a `scenario_name`
column, `scenarios` (notes), `groups`, `group_members` and `hcr_eligible`. An
admin exports the workbook, edits it in Excel and imports it through the admin
API; each import is checked (structure refused, contract mismatches
reported), applied all or nothing, and kept as a version. A **default workbook**
ships in the backend (`catalog/data/default_catalog.xlsx`) and is loaded as
the first version on a fresh install (`surimi-backend seed-catalog`, run by the
migrate job after `seed-species`); it is never loaded over admins' data except
through an explicit reset. The species list of a scenario still comes from the
live contract on every request; the database holds only what the contract
lacks. The generator script becomes a developer tool that builds or refreshes
the default workbook from ASFIS and the partner repos. The workbook is read
and written with `openpyxl`.

## Why

- Admins can fix a name or add the Aegean groups the day they get them, with
  no developer or deploy; 0017's "no admin UI" is answered by the workbook,
  which needs no UI and works through Bruno or the console now.
- One workbook for all scenarios, with species once, matches the data: names
  are global, groups and eligibility are per scenario.
- Workbook = database keeps export and import exact: what an admin downloads
  is what the system uses.
- 0017's "harder to review" is answered by the dry-run report (what an import
  adds, changes and removes) and by keeping every imported workbook with who
  imported it.
- 0017's "hand copies drift" is answered by checking every import and every
  contract fetch against the live contract, and by the generator, which can
  rebuild the default from the partner repos.
- The whole ASFIS list (13,567 species; 315 codes in use on 2026-11-16) gives
  a name to any code a contract adds later without a new release (user,
  2026-11-16, reversing the 315-code subset of 2026-11-13).

## Alternatives considered

| Option | Why not |
| --- | --- |
| Keep generated JSON files in git (0017) | Every change needs a developer and a deploy; data that is in no repo (Aegean groups) has no place |
| Partners maintain the workbook, or it is regenerated from their repos on a schedule | The user chose admins as the only maintainers (2026-11-13); partner changes come in through a new default built by the generator |
| One workbook per scenario | Species would repeat per scenario; one upload could leave scenarios inconsistent with each other |
| Admin REST endpoints per entity (add group, rename species) instead of a workbook | Hundreds of rows to edit without a UI before phase 10; a workbook is how the partners already exchange this data |
| Read species names from the contract over gRPC | The contract has none (`Species` is code, length class, age, life stage) |
| CSV files instead of one workbook | Five files to keep together; admins open them in Excel anyway |
| Only the codes in use (315) | Chosen on 2026-11-13, reversed by the user on 2026-11-16: a code a contract adds later would have no name until a new list ships |
| pandas to read the workbook | Large dependency for five small tables, and it guesses column types, the conversion that breaks codes |

## Consequences

- New tables `species`, `catalog_scenarios`, `catalog_groups`,
  `catalog_group_members`, `catalog_hcr_eligible`, `catalog_versions`
  (migration), and admin endpoints to export, import (dry run first), list and
  restore versions, and reset to the default. New dependency `openpyxl`.
- The JSON files in `catalog/data/` are replaced by `default_catalog.xlsx`, a
  binary file in git (`.gitattributes` already marks `*.xlsx` binary): its
  changes are reviewed through the generator's or the import's report, not a
  text diff.
- The catalog service reads the active version from the database instead of
  files loaded at start-up; unit tests and `CONTROLLER_MODE=fake` read the
  default workbook into memory.
- Partner changes no longer reach the system by themselves: a developer reruns
  the generator and ships a new default, and an admin imports it (or merges it
  into their own workbook).
- Uploads are admin-only, size-limited and checked as zip archives before
  parsing.
