# SURIMI model GUI

Web application for the SURIMI project: users set up fisheries and ecosystem
experiments (Ecopath with Ecosim, market, fisheries authority and stock
assessment models), run them on the SURIMI controller on the EDITO datalab, and
view the outputs on dashboards. Three case studies: `aegean_sea`, `anchovy_bay`,
`northwestern_med`.

## Scope: infrastructure and backend first, frontend last

Phases 1 to 9 build infrastructure and backend only. Do not build frontend
functionality for the new features (auth, experiments, queue, notifications,
outputs, admin); the backend delivers its REST API, OpenAPI document and Bruno
requests. Structural work that keeps the existing app building (like the
phase 1 move) is fine. Feature docs list what the frontend will need under
"Frontend (phase 10)". **Phase 10, the frontend refactor, is the last phase:
before starting it, ask the user whether they want it done** (user,
2026-11-03).

**User-authorized exception, 2026-11-05:** T05 removes browser gRPC and centralizes fixed frontend fixtures before later backend phases. The user additionally approved the Axios/Zod request, REST services and TanStack server-state foundation in T06 on 2026-11-05 (ADR 0017). Login UI, guards and live API integration remain next. Do not change backend, protocol, CI or deployment files for frontend tasks. See `docs/implementation-plan/`.

## Before changing anything

1. If the task touches a feature, read `docs/features/<name>/README.md` and its
   `CHANGELOG.md` first.
2. Check `docs/ISSUES.md` for an open item on the same code.
3. If the task depends on how the controller or a model service behaves, check
   `docs/ARCHITECTURE.md` § "Controller behaviour" and then the service's
   source on GitHub with `/surimi-services`. Never assume controller behaviour.
4. Check `docs/decisions/` before choosing a library, protocol or pattern. Do
   not go against an accepted ADR silently: propose a new ADR that supersedes it.
5. For a new feature, use `/feature`. The design is written before the code.

## Before saying the work is done

Do this without being asked. `/record` runs the same steps.

1. Dated entry in the feature `CHANGELOG.md`: what changed, which files, what
   was verified and what was not.
2. Entry in `docs/CHANGELOG.md` when the change is user-visible or needs a
   deploy step.
3. `docs/ISSUES.md`: remove what is fixed, add what was found.
4. `docs/ARCHITECTURE.md` when a container, protocol, table or flow changed;
   `docs/database/schema.dbml` when a table, column, index or enum changed.
5. API changes update the Bruno collection (`/bruno`) and, for the backend, the
   OpenAPI examples. Config changes update `deployments/.env.example` (and
   `apps/frontend/.env.example` for Vite settings).
6. Search `docs/`, `README.md` and app READMEs for every changed name, path, env
   var or endpoint and fix each stale mention.
7. Report which doc files were touched.

## Writing rules for the docs

- Absolute dates (`2026-11-03`), never "today" or "last week".
- Say how each statement is known: **Verified** (ran it), **Read from source**
  (read code, proto or config, not run), **Open question** (needs an answer),
  **Proposed** (a design not yet confirmed by the user).
- A fact confirmed by the user or a partner team (for example Rik for the
  controller) is recorded as confirmed and the matching open question is deleted
  everywhere it appears.
- Diagrams are Mermaid, in the Markdown file, following `docs/DIAGRAMS.md`.

## Facts that are easy to get wrong

- The controller (`surimi.v1.ControllerService`) has no users, no auth and no
  cancel RPC; `RemoveExperiment` is the only way to stop an experiment. The
  client chooses the `experiment_id`.
- `SimulationStatus.status` is a free string, not an enum. The controller sets
  exactly `Initialising`, `Initialised`, `Running`, `Finished`, `Error`,
  `Canceled` (American spelling). A failed initialisation stays `Initialising`.
- `RemoveExperiment` cancels only `Running` simulations and returns success even
  when it cancelled nothing.
- One Ecopath pod per simulation; 10 pods on `project-surimi`. An MSE experiment
  has `NR_OF_MSE_RUNS` simulations (5 there), a non-MSE one has 1.
  "No available pods" is not returned by `SubmitExperiment`; it happens in the
  background and leaves the simulation `Initialising`.
- The controller keeps all experiments in memory: a restart forgets them.
- Frontend gRPC files/dependencies were removed in T05 (2026-11-05). Fixtures/content live in `apps/frontend/mock-data/`. All cases use the same report; setup creates no run. Buf CLI remains at root for Python stub generation.
- Roles are `admin` and `member` (the original request said SimpleUser). SSO
  users' roles come from a configurable claim and are recomputed at every
  sign-in; do not let the admin UI edit them.
- SSO is generic OIDC; Keycloak is only the first provider. No
  Keycloak-specific libraries.
- SSO and local users are separate accounts, never linked by e-mail
  ([ADR 0016](docs/decisions/0016-separate-sso-and-local-accounts.md)). An SSO
  user is found by `identities (provider, subject)`; `users.id` is the
  identifier. E-mail is unique across all users; a first SSO sign-in with a
  missing, unverified or taken e-mail is refused. An SSO user's e-mail and
  names follow the provider at every sign-in.
- Two different queues: Procrastinate for internal jobs, and the experiment
  admission queue, which is the `queued` state in `experiments`
  ([ADR 0015](docs/decisions/0015-experiment-admission-queue.md)).
- The database is `surimi_modelgui_db`. One application user, `surimi_modelgui`,
  runs the migrations and the app; the instance admin is used only by the
  bootstrap job. No PostgreSQL extensions.

## Line endings

Every text file is LF, never CRLF (user, 2026-11-03). `.gitattributes`
(`* text=auto eol=lf`) makes Git store and check out LF on every OS;
`.editorconfig` and `.vscode/settings.json` make editors write LF. When a
script writes files on Windows, write bytes, or pass `newline="\n"` to
`open()` and `Path.write_text()`: without it Python turns every `\n` into
`\r\n` there. Check with a byte-level scan, not `grep $'\r'`, which can reach
grep as an empty pattern and silently match everything.
